# Official FSD v2.1 Migration Design

## Goal

Migrate the existing standalone Next.js application from its custom layered structure to the official Feature-Sliced Design v2.1 structure without changing application behavior.

## Scope

The migration changes project structure, imports, architecture checks, dependency metadata, and architecture documentation. It preserves routes, rendered behavior, validation, API semantics, accessibility, tests, environment contracts, and deployment behavior.

The migration does not add product features, backend behavior, authentication, persistence, localization, generated contracts, or new state-management patterns.

## Target Architecture

Next.js App Router files move from `src/app/` to root `app/`. These files remain thin framework adapters.

FSD layers live under `src/`:

```text
app/                      Next.js App Router adapters
src/
  _app/                   application initialization and route-wide composition
  _pages/                 page slices
  shared/                 reusable infrastructure without business logic
  test/                   project test infrastructure
```

No `features/`, `entities/`, or `widgets/` layer remains. Current workflows and page compositions have one page consumer each, so FSD v2.1 pages-first ownership applies.

## Layer Responsibilities

### Root `app/`

Owns Next.js route files, layouts, metadata adapters, route lifecycle boundaries, favicon, and framework-required global entry files. Route pages re-export their component and metadata from the matching `src/_pages/<slice>` public API.

### `src/_app/`

Owns global providers, route-wide layouts, fonts, global styles, query-client configuration, and global asynchronous-error reporting. The application shell lives in the `layouts` segment. `_app` may import `_pages` and Shared. It contains segments, not slices.

### `src/_pages/`

Contains `home`, `login`, `dashboard`, and `settings` slices. Each slice has a public `index.ts`. Page-specific UI lives under `ui/`; schemas and stateful validation logic live under `model/`; page-specific fetching lives under `api/` only when needed.

Current mappings:

- `src/widgets/home-page.tsx` becomes `src/_pages/home/ui/home-page.tsx`.
- `src/widgets/login-page.tsx`, `src/features/auth/login-form.tsx`, and its schema/tests become the `login` page slice.
- `src/widgets/dashboard-page.tsx`, `src/features/activity/activity-feed.tsx`, and its schema/tests become the `dashboard` page slice.
- `src/widgets/settings-page.tsx`, `src/features/settings/settings-form.tsx`, and its schema/tests become the `settings` page slice.
- `src/widgets/app-shell.tsx` becomes route-wide composition at `src/_app/layouts/app-shell.tsx` and is exported through the layouts segment public API.

The dashboard slice owns its existing activity request because no other page consumes it. Its `api/` segment contains the validated request function and a TanStack Query v5 factory built with `queryOptions`. The UI consumes that factory through `useQuery` instead of declaring query keys and query functions inline.

### `src/shared/`

Keeps reusable, business-agnostic API, environment, UI, route, and library infrastructure. Shared uses segment-level public APIs. Consumers do not import segment internals directly.

Global provider composition and application-specific query defaults move from Shared to `_app`. Generic utilities remain Shared.

## TanStack Query Integration

TanStack Query follows the official FSD integration pattern while preserving the pages-first rule:

- `src/_app/providers/query-provider.tsx` owns `QueryClientProvider`, development tools, and application-wide query and mutation error reporting.
- `src/_app/lib/query-client.ts` owns QueryClient construction, cache callbacks, browser/server client lifetime, and application defaults.
- `src/_pages/dashboard/api/activity.queries.ts` owns the hierarchical activity query key and `queryOptions` factory because the query has one page consumer.
- `src/_pages/dashboard/api/get-activity.ts` owns the activity request and validated response conversion.
- `src/shared/api/` keeps only the generic native-fetch transport, normalized result, and response parsing infrastructure.
- Tests create a fresh QueryClient with retries disabled and infinite garbage-collection time.

No Shared query catalog, entity slice, mutation factory, pagination, Suspense query boundary, server prefetch, dehydration, or cache persistence is introduced without a concrete use case. The existing activity query keeps explicit loading, recoverable error, empty, success, and retry states.

## Public APIs

Every page slice exports framework-consumed page components and metadata through `index.ts`. Server-only exports use a separate `index.server.ts` only if a runtime boundary requires it.

Shared exposes one public API per segment, such as `src/shared/ui/index.ts` and `src/shared/api/index.ts`. No top-level `src/shared/index.ts` is created.

Cross-layer consumers import public APIs. Files inside one slice or segment may use relative imports for their own internals.

## Import Direction

Allowed direction:

```text
_app -> _pages -> shared
```

Root Next.js route adapters may import `_app`, `_pages`, and Shared as required by framework integration. `_pages` slices cannot import sibling page slices. Shared cannot import `_app` or `_pages`.

Client modules cannot import `server-only`, `.server` modules, or `/server/` paths.

## Migration Strategy

Migration proceeds incrementally:

1. Add official FSD validation and teach the local architecture checker the target layers and public-API rules.
2. Establish `_app`, root App Router adapters, and Shared public APIs.
3. Migrate one page slice at a time: home, login, dashboard, settings.
4. Remove obsolete widgets/features directories only after their final consumers move.
5. Update repository architecture documentation and `SPEC.md` after implementation evidence exists.

Each increment updates imports and runs the smallest relevant checks. Temporary hybrid structure is allowed only during execution; final verification requires the target structure.

## Dependency Change

Add the `steiger` core/CLI package and the `@feature-sliced/steiger-plugin` FSD rules package as exact development dependencies using Bun. Add a non-writing architecture command that runs Steiger with the plugin. Keep `package.json` and `bun.lock` aligned. No other dependency changes are authorized.

## Architecture Enforcement

The local architecture checker will enforce:

- `_app`, `_pages`, and Shared downward imports;
- page-slice isolation;
- Client/Server module boundaries;
- public API use across slice and Shared segment boundaries;
- absence of legacy `features`, `widgets`, and unsupported layers in the final structure.

Steiger supplies the architecture-linter runtime, while `@feature-sliced/steiger-plugin` supplies the FSD rules. The local checker owns repository-specific `_app` and `_pages` enforcement, and existing dependency checks remain authoritative for dependency policy.

## Behavior Preservation

All current routes remain:

- `/`
- `/login`
- `/dashboard`
- `/settings`

Loading, error, global-error, not-found, metadata, theme persistence, form validation, activity fetching, normalized errors, responsive navigation, and accessibility behavior remain unchanged.

## Testing and Verification

After each page migration, run its focused Vitest tests plus architecture checks. Final checks:

```text
bun run env:check
bun run architecture:check
bun run fsd:check
bun run dependencies:check
bun run typecheck -- --incremental false
bun run check
bun run test
bun run build
bun run e2e:run
```

`bun run build` must precede `bun run e2e:run`. Generated outputs remain tool-owned.

## Documentation

Update README and canonical `.ai/` guidance to describe official FSD v2.1, root App Router adapters, `_app`, `_pages`, Shared public APIs, and exact commands. Update `SPEC.md` after implementation only where its assessment instructions or expected architecture evidence would otherwise be stale.

AI setup files are not created during this migration. AI readiness assessment resumes after migration verification.

## Workspace Safety

Preserve the existing `.gitignore` modification. Do not stage, commit, push, switch branches, discard changes, or modify unrelated files. Final report separates migration changes from pre-existing work.

## Acceptance Criteria

- Root `app/` contains thin Next.js App Router adapters.
- `src/_app/`, `src/_pages/`, and `src/shared/` follow FSD v2.1 ownership.
- No single-use `features/` or `widgets/` layer remains.
- No premature `entities/` layer exists.
- Page slices and Shared segments expose public APIs.
- Cross-boundary imports use those public APIs.
- TanStack Query provider and client configuration live in `_app`.
- The page-specific activity query uses a colocated `queryOptions` factory and passes TanStack Query cancellation through the shared fetch client.
- Steiger and local architecture validation pass.
- Existing application behavior and routes remain covered by passing tests and E2E checks.
- Architecture documentation and `SPEC.md` match the implemented structure.
- No unrelated or application-behavior change is introduced.
